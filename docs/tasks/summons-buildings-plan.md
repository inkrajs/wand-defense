# 召唤与建筑后续方案

日期：2026-11-03。状态：隔离feature开发中，未合入当前demo。

## 本轮隔离实现采用的原型方案

根协调者已提供独立clone `wand-defense-summons-buildings`，分支 `feature/summons-buildings`，起点d099767。以下是本轮临时实现选择，不代表所有待定规则已由用户确认：

- 采用逐次语义命令deploySpell，字段wandId/itemId/position:{x,y}；没有自动部署锚点，自动战斗不给位置就不生成召唤/建筑。
- 逻辑位置按0..100闭区间的实体中心点校验，允许重叠，无地形阻挡、吸附、占地或部署距离限制；远离防线同样合法。
- 仅battle进行中且未暂停/未开背包、领地存活时执行。每来源同时最多2个，copies须整体满足容量；一次法力消耗与冷却对应全部copies，失败无资源变更。
- 初始角色不再带狼或塔；feature测试通过显式授予/装备来获取部署法术。召唤建筑配置仍只在此feature分支。
- previewDeployment是只读纯API；提交重新校验，runtime统一幂等、发事件、推进战斗。远程命令解析/能力发现复用该runtime，无DOM依赖；本轮未制作战场点选UI。

下文原始方案保留确认/待定划分；其中“等待隔离目录/尚未派发”是上一阶段的历史状态，由本节及文末实际进展取代。
本文件是当前优先级调整的补充；battle.md 的历史实现与验收不代表这些能力进入当前 demo。

- 当前先跑整体流程 demo：projectile/heal、法杖构筑、清波奖励。初始角色不提供建筑功能；初始库存和奖励排除狼、箭塔、元素精灵等召唤/建筑内容。
- 召唤与建筑暂不合入当前版本。已有完整实现由根协调者保存到未合入的 feature 分支；分支名称和保存结果以根协调者记录为准，本负责人不切共享 checkout。
- 后续支持整个战场自由选位置，合法场景内没有“只能放在防线附近”的区域限制。旧实现的召唤 y=78、建筑 y=86 只是过往占位行为，不能沿用为产品规则。
- 位置输入通过语义命令进入同一个权威 runtime。人类交互与 HTTP/CLI 使用同一套规则与校验。
- 当前仅新增本文档，不改共享 engine/content/contracts，不派实现任务。收到根协调者提供的隔离目录和明确文件边界后再开发。

## 位置与施法交互草案（尚未确认）

建议将“法杖格子中的摆放”和“战场中的部署”分为不同语义；现有 placeItem 只处理法杖格坐标，不能借用它部署实体。

建议由公共契约负责人统一设计部署命令，表达 commandId、来源角色/法杖/法术实例、战场 position，以及需要时的状态版本。具体命令名和字段尚未冻结。坐标使用战场逻辑空间，屏幕、缩放和手机触摸坐标只由 UI 转换；是否继续用0..100、是否吸附网格及坐标原点均待定。

自动施法与手动位置之间尚有两种可选机制：先配置某来源法术的部署锚点，让后续自动施法重复使用；或玩家每次发部署命令，立即请求一次受法力/冷却约束的施法。可按法术区分，不能在开发时默认其中一种已确认。没有位置输入时等待、采用默认位置或自动选点也须明确；任何默认策略都不得恢复防线附近的硬限制。

建议提供语义预览：输入来源与位置，返回当前可执行性及允许披露的原因；预览不预留资源。实际执行重新校验，在一次事务内扣法力、更新冷却并生成实体。预览成功不保证稍后的提交成功，重复 commandId 不重复生成或扣费。位置无效或当前容量不足时保持资源与冷却不变。

## 合法位置规则（尚未确认的细化）

“全战场自由放置”已确认；以下合法性细节仍需产品取舍，不能自行添加限制：

| 事项 | 待定内容 | 实现约束 |
| --- | --- | --- |
| 场景边界 | 按实体中心还是完整占地判界，边缘是否容许部分伸出 | 使用逻辑边界，拒绝 NaN/Infinity；不按图片透明边距判定 |
| 地形 | 是否存在不可站立/不可建造的真实地形 | 若存在，由场景配置定义；不凭离防线远近划禁区 |
| 占地与重叠 | 建筑尺寸、召唤物碰撞、与敌人重叠是否允许 | 不默认所有建筑都单点，也不默认一律互斥 |
| 阻挡与寻路 | 建筑是否挡路，封死路线是否允许 | 若采用阻挡，寻路和合法性由引擎统一，UI只展示结果 |
| 部署范围 | 是否存在某些法术自身的特殊距离条件 | 默认不提出部署距离限制；特殊条件须另获确认 |
| 多次施放 | 双重/分裂使用同一点、偏移点还是多个输入点 | 不能绕过占地/容量；整体原子或允许部分成功需先确定 |
| 暂停与阶段 | 战斗中、背包暂停、波间能否部署或调整锚点 | 锚点配置与实际生成是否分别允许须明确 |
| 容量 | 按来源、角色、种类或全队计算，是否允许主动替换 | 旧版每来源2个只是原型数值，不能作为已确认上限 |

## 实体生命周期与行为（尚未确认的细化）

保留已有独立实体、来源追踪、HP、寿命、攻击/治疗配置的分层思路，复用 compileWand 已计算的数值，避免序列或奥术重复叠加。持续时间、实体攻击间隔与召唤法术冷却分别配置；行为按配置分派，不按某个木灵定义 ID 写死。

召唤物是否移动、是否吸引敌人、建筑能否被修复、退场是否释放容量、换杖后是否存续、跨波保留、部署后能否搬移以及退款规则均待定。实现时须明确到期/被击杀/替换/清波等退场原因，敌人收益只结算一次，友军退场不产生敌人击杀收益。暂停冻结行为、寿命和冷却；仅配置动作是否可在暂停中发生另行确认。

## 使用此feature的语义入口

在隔离clone运行`npm run dev`可启动原有界面；本轮部署通过语义接口使用，界面尚无部署按钮。

法术必须是已发现的物品、已装备在归属正确的法杖上，且已开始战斗。初始没有建筑或召唤物；可通过此feature奖励获得部分召唤内容，测试环境可显式本地解锁作弊后授予所需法术，再暂停装备。网络不能执行unlockCheats。

```ts
import { previewDeployment } from './src/engine';
// runtime为现有createGameRuntime创建的同一个权威实例。
const request = { wandId: 'wand-1', itemId: equippedItemId, position: { x: 3, y: 7 } };
const preview = previewDeployment(runtime.getState(), request, demoContent);
const result = runtime.dispatch({ id: 'deploy-unique-1', type: 'deploySpell', ...request });
```

HTTP/CLI使用相同Command JSON，无屏幕节点或DOM选择器：

```json
{"id":"deploy-unique-1","type":"deploySpell","wandId":"wand-1","itemId":"实际已装备物品实例ID","position":{"x":3,"y":7}}
```

事件spell.deployed包含itemId/wandId/characterId和逻辑x/y；生成实体可从同一runtime快照读取。位置表示生成时刻；建筑固定，召唤物以后按自身行为移动。preview成功并不替执行预留资源，实际结果以executed/rejected为准。
